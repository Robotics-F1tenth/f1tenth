## 0-A. 2026-08-19 갱신 — 첫 파이프라인 스모크테스트 통과, 이득 재측정, params 미로딩 버그

**이 절이 §8.5의 -30~35% 수치를 갱신한다.** 이득 방향은 그대로지만 크기가 다르다.

### 발견한 버그: 이 패키지의 params 파일은 그동안 한 번도 로드된 적이 없다

`config/ekf_pose.yaml` 최상위 키가 `ekf_pose_node:` 인데 노드는 스스로를
`ekf_pose_estimator` 로 이름 짓는다. ROS 는 매칭 실패 시 조용히 무시하므로,
**노드는 계속 `declare_parameter()` 기본값으로 돌고 있었다.** 그중 둘은 이 파일의
의도와 정반대다:

| 파라미터 | 파일(의도) | 코드 기본값(실제 적용) | 결과 |
|---|---|---|---|
| `imu_axis_yaw180` | `false` | **`true`** | 지금 드라이버 출력에 ax/ay 를 한 번 더 뒤집어 가속도 경로 오염 |
| `publish_tf` | `false` | **`true`** | `map->base_link` 를 MCL 과 **동시 발행**해 TF 충돌 |

`/**` 와일드카드 키로 수정(`746d4b3`). `ros2 param get` 으로 둘 다 `false` 확인.
**이 상태로 A/B 를 돌렸다면 EKF 가 부당하게 나쁘게 나왔을 것이다.**

### A-1 스모크테스트: 통과 (최초)

§8.5.0 이 "EKF 경로는 실제로 한 번도 동작한 적이 없다"고 적어둔 상태였다. 이번에
live MCL + `ekf_pose` 를 같은 bag replay 에 함께 띄워 **`/ekf_pose` 가 200 Hz 로
정상 출력되는 것을 처음으로 확인**했다(3회 모두 18,650행 내외).

### A-3 이득 재측정 — control 관점(ZOH), 3회 반복

control 은 MCL 보다 빠르게 돌기 때문에 MCL 갱신 사이에는 **직전 pose 를 홀드(ZOH)**
한 값을 쓴다. 그래서 MCL 을 자기 타임스탬프에서만 채점하면 MCL 에 유리하게 왜곡된다.
EKF 시계 위에 MCL 을 ZOH 로 리샘플해 둘 다 같은 시점에서 GT 와 비교했다
(`eval/.../zoh_compare.py`):

| | MCL+ZOH | EKF | 개선 |
|---|---|---|---|
| p50 | 0.102~0.104 m | 0.075~0.078 m | −26% |
| p90 | 0.269~0.273 m | 0.191~0.197 m | −29% |
| MAE | 0.126~0.127 m | 0.100 m | **−20.6% (±0.2%)** |
| RMSE | 0.161~0.162 m | 0.130~0.132 m | **−18.5%** |
| yaw MAE | 2.46~2.47° | 2.09~2.19° | −13% |

3회 반복 재현성이 ±0.2%로 매우 안정적이다. **§8.5의 "-30~35%" 보다는 작다** —
같은 방향, 같은 자릿수지만 그 수치를 그대로 인용하지 말 것. 차이의 원인(측정 프로토콜
차이 vs 설정 차이)은 규명하지 않았다.

> 참고: MCL 을 **자기 타임스탬프**에서만 채점하면 EKF 이득은 MAE −13% 로 줄어든다.
> 어느 쪽이 맞느냐가 아니라 **무엇을 묻느냐**의 차이다 — "추정기 자체가 더 정확한가"는
> 전자, "control 이 실제로 받는 pose 가 더 정확한가"는 후자(ZOH). 제어 전환을
> 판단할 때는 ZOH 쪽이 맞다.

## 1. 모델 검토 — "자전거 모델" 이 아니다

[ekf_pose_estimator.cpp:145](../src/ekf_pose_estimator.cpp#L145) 주석은
"도출 모델 (자전거 모델 + IMU 가속도)" 이라고 되어 있지만, 실제 코드는:

```cpp
px  += (vx*cos(yaw) - vy*sin(yaw)) * dt
py  += (vx*sin(yaw) + vy*cos(yaw)) * dt
yaw += yaw_rate * dt
vx  += (ax - vy*yaw_rate) * dt
vy  += (ay + vx*yaw_rate) * dt
yaw_rate = IMU 측정값 (직접 대입)
```

- 조향각 입력이 **없다**
- `l_f`, `l_r`, 휠베이스가 **어디에도 안 쓰인다**
- 타이어 모델이 **없다**

이건 **자전거 모델이 아니라 IMU 구동 점질량 데드레커닝**이다. 그 자체로는
로컬라이제이션 EKF 로서 타당한 선택이다 (모델 프리라 차량 파라미터 오차에 강건).
다만 주석이 사실과 달라 오해를 부르므로 고쳐야 한다.

### MPPI ego 모델과의 관계 — 다르다

| | ekf_pose | smppi_cuda_controller |
|---|---|---|
| 모델 | 운동학 점질량 + IMU | 파세이카 동역학 자전거 |
| 상태 | x,y,yaw,vx,vy,yaw_rate | x,y,yaw,v,vy,omega,ay,slip_angle |
| 타이어 | 없음 | 4-파라미터 매직 포뮬러 |
| 조향 입력 | 안 씀 | 씀 |

**두 모델은 일관되지 않는다.** 로컬라이제이션과 플래닝이 다른 모델을 쓰는 것
자체는 흔하고 문제될 게 없지만, 결과적으로 **MPPI 가 필요로 하는 `slip_angle` 을
EKF 가 신뢰성 있게 줄 수 없다**는 구조적 한계가 생긴다 (§4, §5).

#### 왜 파세이카 모델을 상태추정에 그대로 안 쓰나 (2026-08-04 추가)

"플래닝에 이미 정교한 동역학 모델이 있는데 estimator 도 그걸 쓰면 안 되나"는
자연스러운 질문이다. 안 쓰는 게 맞다 — 이유 세 가지:

1. **역할이 다르다.** SMPPI 의 파세이카 모델은 지금 상태에서 **후보 제어입력을
   넣었을 때 미래가 어떻게 될지 굴려보는(rollout) 시뮬레이터**다. estimator 는
   반대로 **잡음 섞인 센서에서 지금 상태가 뭔지 역산**하는 게 일이다. "미래를
   예측하는 모델"과 "현재를 추정하는 모델"은 같은 물리 방정식이어도 요구사항이
   다르다 — 후자는 파라미터 오차에 강건해야 하고, 실시간으로 매 IMU 샘플마다
   야코비안까지 계산해야 한다.
2. **파세이카 모델의 파라미터 자체가 지금 불확실하다.** `smppi-diagnosis-2026-08.md`
   C-4 가 이미 지적했듯 sysid 로 뽑은 후륜 계수 `C_r=2.2129` 는 승용 타이어
   통상범위(1.3~1.8)를 벗어난 비물리적 값이고, 피크 이후 힘이 급붕괴하다가
   부호까지 뒤집힌다. **이런 모델을 estimator 의 예측 단계에 그대로 넣으면,
   모델 오차가 "위치를 추정하는 기준값" 자체를 오염시킨다.** 지금 EKF 처럼
   거의 파라미터 없는(질량점 + IMU) 모델을 쓰면 이 위험이 원천 차단된다 —
   추정이 제어 모델의 오류에 종속되지 않는 **독립적인 체크**로 남는다.
3. **저속에서 수치적으로 불안정하다.** 같은 문서 C-3: 이 차량의 요 동역학은
   2 m/s 이하에서 오일러 적분(35ms 스텝) 자체가 발산·진동한다(코너 저속구간이
   하필 이 영역). estimator 의 predict 단계에 이 모델을 쓰면, 모델의 수치
   불안정성이 **추정치 자체에 스퓨리어스 진동으로 새어 들어간다** — 지금의
   단순 운동학 모델엔 이런 극이 없어서 이 문제가 아예 없다.

**완전히 무관하지도 않다** — P1(§5, §9)의 `β = atan(l_r·ω/v)`는 파세이카 모델과
**같은 단일트랙 기하**(l_r)를 쓴다. 다만 빌린 건 통계적으로 식별해야 하는 타이어
힘 파라미터(B,C,D)가 아니라 **직접 실측 가능한 기하 파라미터(축거) 하나뿐**이라
불확실성이 훨씬 적다. 즉 "플래닝 모델을 통째로 재사용"은 안 하지만, **그 중
안전한 부분(기하)만 이미 재사용하고 있다** — 이게 estimator 와 planner 모델을
분리하면서도 얻을 수 있는 절충점이다.

## 3. Coriolis 부호 — 코드와 센서의 오류가 서로 상쇄되고 있다 ★

[ekf_pose_estimator.cpp:180-181](../src/ekf_pose_estimator.cpp#L180-L181):

```cpp
vx += (imu.ax - vy*yr) * dt      // 교과서: vx += (ax + vy*w)dt
vy += (imu.ay + vx*yr) * dt      // 교과서: vy += (ay - vx*w)dt
```

**코드가 교과서와 부호가 반대다.** 그런데 §2 에서 IMU 의 ay 도 반전되어 있다.
`ay_meas = -ay_true` 를 대입하면:

```
v̇y_ekf = ay_meas + vx*w = -(v̇y_true + vx*w) + vx*w = -v̇y_true
```

**즉 현재 EKF 의 v_y 는 부호만 반대이고 크기는 대략 맞는다.** 두 개의 오류가
서로를 부분적으로 상쇄하고 있다.

### ⚠ 치명적 상호작용 — 한쪽만 고치면 8배 악화된다

1초 윈도우마다 mocap v_y 로 초기화 후 적분, 종점 오차 (RMSE, m/s):

| 적분식 | bag 22:52:38 | bag 22:25:24 |
|---|---|---|
| 현재 EKF `vy += (ay + vx*w)dt` | 0.356 | 0.392 |
| **교과서 `vy += (ay - vx*w)dt`** | **2.976** | **3.954** |
| ay 부호수정 + 교과서 `vy += (-ay - vx*w)dt` | 0.343 | 0.453 |
| `vy = 0` 고정 (현 실차 동작) | **0.073** | **0.178** |
| *(참고) 실제 mean\|v_y\|* | *0.078* | *0.196* |

**누군가 "Coriolis 부호가 틀렸네" 하고 교과서 형태로만 고치면 오차가 8~10배로
폭발한다.** IMU 축 반전을 같이 고쳐야 한다. 반드시 세트로 처리할 것.

## 4. 그런데 — IMU 적분으로는 v_y 를 얻을 수 없다 ★★

위 표의 마지막 두 줄이 핵심이다.

**어떤 부호 조합을 쓰더라도 IMU 적분 오차(RMSE 0.34~0.45 m/s)가 추정 대상
(|v_y| ≈ 0.08~0.22 m/s)보다 2~5배 크다. `v_y=0` 으로 두는 게 IMU 적분보다 낫다.**

신호 대 잡음비가 1 미만이다. 1초만 개루프 적분해도 결과가 무의미해진다.
`state_assembler.py` 의 워시아웃(τ=2.0s)은 이 드리프트를 묶어주려는 장치지만,
SNR 이 이 정도면 워시아웃이 결국 값을 0 근처로 끌어당길 뿐이라 **결과적으로
`v_y=0` 과 크게 다르지 않게 된다** (게다가 τ=2s 는 위 테스트의 1s 보다 긴 적분이다).

> **이전 권고 정정**: `smppi-diagnosis-2026-08.md` Phase 1-A 에서 "①
> state_assembler 재사용(★ 이미 검증된 코드)" 을 1순위로 제시했으나, **이 데이터로
> 기각한다.** 그 코드는 pacejka_sysid 의 오프라인 파라미터 식별 용도로는 (구간을
> 골라 쓰므로) 여전히 유효할 수 있으나, **온라인 상태추정용으로는 부적합**하다.

### 4.1 왜 적분 오차가 이렇게 큰가 — 메커니즘 (2026-08-04 추가)

**핵심은 축 반전 버그가 아니다.** §3 표를 다시 보면: 축 반전을 고친 버전(`ay
부호수정 + 교과서`)도 RMSE 0.343/0.453 — 안 고친 버전(0.356/0.392)과 **거의
같다.** 축이 맞든 틀리든 오차 크기가 안 변한다는 게 결정적 증거다 — 즉
"부호가 틀려서" 못 쓰는 게 아니라 **애초에 가속도계 적분이라는 방법 자체가
이 크기의 신호엔 안 맞는다.**

**메커니즘**: 가속도계가 실제로 내놓는 값은 `측정 = 참값 + 바이어스 + 노이즈`다.
이걸 **한 번 적분**해서 속도를 얻으면:

```
v(t) = ∫(참값+바이어스+노이즈) dt = v_true(t) + 바이어스·t + ∫노이즈 dt
```

바이어스 항은 **시간에 비례해서 무한정 자란다** — 잠깐이라도 열리면 못 닫는
개루프(open-loop)다. MEMS급 저가 IMU의 바이어스 불안정성은 보통 수 mg
(0.01~0.05 m/s²) 수준인데, 이걸 1초 적분하면 그것만으로 0.01~0.05 m/s 오차가
쌓인다 — 게다가 실측 RMSE(0.34~0.45)는 이보다 한참 크므로, 여기에 노면
진동·크로스축 민감도·미보정 피치/롤 성분까지 같이 새어 들어온 것으로 보인다.

**그런데 추정하려는 신호(|v_y| ≈ 0.08~0.22 m/s) 자체가 이 오차보다 작다.**
신호 대 잡음비(SNR) < 1 — "잡음이 신호보다 큰" 상태다. 통계적으로 이건
좋은 필터를 써서 해결될 문제가 아니다(§4 워시아웃 논의 참고 — 결국 0으로
수렴할 뿐). **입력 자체에 신호가 없으면 어떤 후처리도 신호를 만들어내지 못한다.**

이래서 §5 의 운동학 추정(`β = atan(l_r·ω/v)`)이 통하는 것 — 그건 가속도계를
**아예 안 거친다.** 자이로(z축, 정상·15ms 신선·corr 0.95)와 휠 오도메트리(v,
정상)만 쓰고, "횡가속도를 적분해서 얻는" 대신 "정상상태 코너링에서 슬립각과
각속도/속도 비율이 기하학적으로 고정된다"는 **다른 물리 관계**를 이용한다.
가속도계의 결함이 있는 채널을 안 쓰는 것 자체가 해법이다.

## 5. 그럼 슬립각을 어떻게 얻나 — 운동학 추정이 실제로 통한다 ★

### 5.1 먼저: mocap 슬립각에는 레버암 오염이 있다 (방법론 주의)

강체에서 각속도는 모든 점에서 같지만 횡속도는 기준점에 따라 다르다:
`v_y(P) = v_y(CoG) + x_p·omega`. mocap 마커 중심이 CoG 가 아니면 슬립각이 통째로
오염된다. 실제로 보정 전에는 운동학 모델과 **음의 상관**(-0.45/-0.72)이 나와
물리적으로 말이 안 됐다.

저속(0.8~1.5 m/s, 운동학 모델이 잘 성립하는 영역)에서 오차를 최소화하는 `x_p` 를
스캔해 역산:

|---|---|---|
| 22:52:38 | **+0.200 m** | 마커 중심이 CoG 앞 20cm |
| 22:25:24 | **+0.250 m** | 마커 중심이 CoG 앞 25cm |

두 bag 에서 부호와 크기가 일관된다. (세션마다 값이 다른 건 `0730-bag-benchmark.md`

> 운동학 추정기를 평가하는 건 부분적으로 순환논리다. 다만 **적합한 건 스칼라 하나뿐**
> 이고 평가는 훨씬 넓은 속도 구간(v>1.0)에서 시간변동 신호 전체에 대해 이뤄지므로
> 완전한 순환은 아니다. 절대 슬립각 크기는 이 보정의 정확도에 의존한다.

**SMPPI 는 이 값을 전부 0 으로 보고 매 35ms 마다 플래닝을 시작하고 있다.**

### 5.3 운동학 추정기가 실제로 잘 맞는다

`beta = atan(l_r · omega_gyro / v_odom)` — 자이로(정상 축)와 휠 오도메트리(정상)만
쓰므로 **고장난 가속도계를 아예 안 탄다.**

| 추정식 | RMSE (22:52:38) | RMSE (22:25:24) | corr |
|---|---|---|---|
| `beta = 0` (현재) | 5.61° | 9.21° | — |
| **`beta = atan(l_r·w/v)`** | **2.50°** | **5.60°** | **+0.89 / +0.95** |

**슬립각 오차를 45% / 39% 줄이고, 상관계수가 +0.89~0.95 다.** 한 줄짜리 변경으로
얻는 개선치고 매우 크다.

## 6. yaw_rate — 좋은 신호를 나쁜 신호가 끌어내리고 있다

mocap 기준 (각속도는 레버암 영향 없음 — 강체 전체에서 동일하므로 이 비교는 오염 없음):

| 소스 | RMSE | 지연 | 코너에서 |
|---|---|---|---|
| `/imu/data` 자이로 | 0.34 / 0.40 rad/s | **+5~15 ms** | 실제의 0.85~0.95배 |
| `/odom` angular.z (운동학 `v·tanδ/L`) | 0.58 / 0.69 rad/s | **+110~115 ms** | 실제의 **0.70~0.80배** |

`/odom` 의 각속도는 측정이 아니라 [vesc_to_odom.cpp:111](../../vesc/vesc_ackermann/src/vesc_to_odom.cpp#L111)
의 운동학 재구성이다. **코너에서 실제보다 20~30% 낮고 115ms 늦다.**

그런데 EKF 는 [ekf_pose_estimator.cpp:296](../src/ekf_pose_estimator.cpp#L296) 에서
`H(2,5)=1.0` 으로 이 신호를 `r_odom_yaw_rate=0.05` (꽤 타이트)로 융합한다.
**15ms 신선하고 정확한 자이로 값이, 115ms 묵고 25% 낮은 운동학 값에 끌려간다.**

> 기울기 0.85 는 회귀의 감쇠편의(errors-in-variables)일 수 있다. 역회귀 역수는
> 0.95 이므로 자이로의 참 스케일은 0.85~0.95 사이 — 1.0 을 포함하지 않아 실제로
> 약간 낮게 읽는 것으로 보이나, mocap 미분 노이즈 때문에 단정하기 어렵다.

## 7. EKF 공식 자체의 문제

### 7.1 야코비안이 상태전이와 일치하지 않는다

predict 에서 `yr_new = imu.yaw_rate` **직접 대입**([:182](../src/ekf_pose_estimator.cpp#L182))인데,
야코비안은 `F(5,5)=1` (즉 `yr_new = yr_old`)로 두고 `Q(5,5)` 를 더한다.
**상태는 외부 입력으로 덮어쓰면서 공분산은 "이전 값이 유지됐다"고 전파한다.**
`P(5,5)` 가 실제 불확실성을 반영하지 못하므로, 이어지는 odom yaw_rate 업데이트의
칼만 게인이 잘못 계산된다.

올바른 처리: yaw_rate 를 상태에서 빼고 IMU 를 제어입력 `u` 로 다루거나(그러면
`Q` 에 IMU 노이즈를 반영), 상태로 유지하되 IMU 를 **측정치로 update** 해야 한다
(직접 대입이 아니라).

### 7.2 vy 측정치가 가짜다 (기존 B-2)

`H(1,4)=1.0` 으로 `/odom` 의 `twist.linear.y` 를 vy 측정치로 융합하는데, 그 값은
[vesc_to_odom.cpp:157](../../vesc/vesc_ackermann/src/vesc_to_odom.cpp#L157) 에서
`0.0` 하드코딩이다. IMU 예측이 만든 vy 를 매번 0 으로 끌어내린다.

단, §4 에 따르면 **그 IMU 예측 자체가 못 쓸 물건**이라 결과적으로는 vy=0 이
최선에 가깝다. 즉 이 "버그"가 현재는 오히려 방어 역할을 하고 있다. 고칠 때는
§4·§5 를 함께 반영해야 한다.

### 7.3 MCL 지연 보상이 없다

`ekf_update_pose` 는 MCL pose 를 **현재 상태**에 그대로 적용한다. MCL pose 는
스캔 취득→파티클 필터 연산을 거친 과거 시점의 추정이다. 표준 처리는 상태를
측정 시각으로 되돌려 업데이트한 뒤 다시 전진시키는 것(retrodiction)이다.

### 7.4 발행 타임스탬프가 상태 유효시각이 아니다

`publish_pose(this->now())` — 벽시계 현재 시각으로 발행한다. 상태가 실제로
유효한 시각(마지막 predict 시각)이 아니므로 소비자 쪽 시간 정합이 깨진다.

### 7.5 초기화 경로의 락 누락

`mcl_pose_callback` 의 초기화 분기에서 `initialize_state()` 와 `ekf_predict()` 를
`state_mutex_` **없이** 호출한다([:381-392](../src/ekf_pose_estimator.cpp#L381-L392)).
`imu_callback` 이 `initialized_` 를 락 없이 읽는 것과 겹쳐 경합 가능.

## 8.5. EKF 를 쓸 것인가, MCL 을 그냥 쓸 것인가 ★★ (결정적 실험)

> "MCL 이 35Hz 정도 나오는데 그냥 쓰면 안 되나? 보간하면 오히려 오차만 더 늘어나는
> 거 아닌가? EKF 떼는 게 나을지도" 라는 질문에 대한 정면 답.

### 8.5.0 먼저 — 지금 EKF 는 제어 루프에 들어있지 않다

| 런치 | pose 소스 | 상태 |
|---|---|---|
| `smppi_cuda_controller/launch/cuda_mppi.launch.py` (실차 기본) | **`/newmcl_pose` 직접** + `/odom` | 실제로 쓰이는 경로 |
| `ekf_pose/launch/smppi_with_ekf.launch.py` | `/ekf_odom` | **실행 불가 상태였음** |

`smppi_with_ekf.launch.py` 는 세 군데가 깨져 있었다 (2026-08-03 수정함):
1. 존재하지 않는 `smppi_params.yaml`, `path_publisher.yaml` 참조 (실제 파일은 `params.yaml`)
2. 실행파일 이름 `ekf_pose_node` → 실제 타깃은 `ekf_pose_estimator`
3. `use_mcl_pose:false` 미설정 → smppi_node 가 기본값 `true` 로 떠서 정성껏 지정한

**즉 "EKF 로 보간해서 쓴다"는 경로는 한 번도 동작한 적이 없다.** 현재 실차는
MCL pose 를 ZOH(영차유지)로 그냥 쓰고 있다.

### 8.5.1 MCL 은 35Hz 가 아니라 50Hz 다

| 토픽 | 수신율 | dt p95 | 헤더→수신 지연 |

**① EKF 는 유지하는 게 맞다.** 위치 오차를 **30~35%** 줄인다 (12.11→8.52cm, 11.01→7.12cm).

**② "보간해서 오차가 늘어나는 것 아닌가" 걱정은 타당하지만, EKF 의 이득은 보간에서

**③ 단순 등속외삽(B)만 해도 -8~-11%** 는 얻는다. 즉 이득의 1/3 정도는 그냥 지연

빼면 raw MCL 보다 좋아진다.

업데이트가 20ms 마다 vx/vy 를 덮어써서 IMU 예측 기여분이 원래 작기 때문이다.
그래도 고쳐야 하는 이유는 (a) 물리적으로 틀렸고 (b) 누군가 vy 행을 빼는 순간
(E안) 바로 문제가 되며 (c) Coriolis 부호 수정과 세트여야 하기 때문이다.

**⑥ odom vy 행(가짜 0)은 빼지 말 것** (E vs G: 9.30/21.60 vs 8.52/20.33,
bag2 는 7.91 vs 7.12 로 더 뚜렷). §4 대로 IMU 적분 vy 가 못 쓸 물건이라,
그 가짜 `0` 측정치가 **오히려 발산을 막아주는 clamp 역할**을 하고 있다.

## 9. 권고 — 우선순위

### 우선순위 재검토 (2026-08-04, control 측 실험 결과 반영)

`smppi-diagnosis-2026-08.md`(D''절)가 시뮬 폐루프에서 상태추정 품질(B-2, vy)이
실제 증상(코너 인코스 파고들기, S1)의 원인인지 직접 실험했다 — `assume_zero_vy`
주입으로 vy 정상 vs vy=0 강제를 같은 조건 6회씩 비교:

```
거리 차이 10.3m, 표준오차 14.7 → t≈0.70  (유의하지 않음)
이탈비율 차이 12.0%p, 표준오차 10.1 → t≈1.19  (유의하지 않음)
```

**n=6에서 "vy 품질이 S1의 원인"이라는 가설은 확증도 기각도 안 됐다** (확증하려면
20~30회 필요). 더 중요한 부수 발견: **완벽한 모델 + 완벽한 상태추정(vy 정상) 조건
에서도 주행시간의 24~27%를 트랙 경계 밖에서 보낸다.** 즉 상태추정을 얼마나
개선해도 안 없어지는 문제가 따로, 그것도 더 크게 있다는 뜻 — 그 문서는 **비용함수
구조(Phase 3: barrier cost, 요구값 기반 그립 페널티)를 상태추정(Phase 1)보다
앞이나 최소 동급으로** 올릴 것을 권고했다.

**이게 ekf_pose 작업에 주는 의미**:
- ekf_pose 자체의 검증된 가치(§8.5, raw MCL 대비 위치오차 -30~35%)는 **그대로
  유효하다** — 이건 순수 localization 품질 측정이고 S1 인과관계와 무관하게 참이다.
- 다만 **"이걸 더 다듬으면 S1(코너 파고들기)이 고쳐질 것"이라는 기대는 과장하지
  말 것** — 그 인과관계는 아직 통계적으로 안 잡혔고, 잡혀도 지배적 요인이 아닐
  가능성이 이미 시사됐다.
- 아래 P0~P3 는 **estimator 자체의 정확성/정합성 개선**으로서 계속 진행할 가치가
  있음(공짜거나 저비용, 손해 없음) — 다만 "S1을 잡기 위한 최우선순위"로 프레이밍
  하지는 않는다. **S1을 실제로 움직이려는 다음 투자는 `smppi_cuda_controller`의
  Phase 3(비용함수)**로 가는 게 맞다 — 이건 이 문서(ekf_pose) 범위 밖.
- 정말 vy/슬립각 정확도가 S1에 영향 있는지 확정하고 싶다면, `assume_zero_vy`
  테스트를 **조건당 20~30회로 재실행**하는 게 다음 ekf_pose 관련 실험으로는

## 11. Retrodiction 구현 + A/B 실측 (2026-08-04)

### 11.1 설계

MCL pose 는 스캔취득→파티클필터 연산을 거친 **과거 시점**의 추정인데, 그동안
`x_`/`P_`는 IMU 로 이미 더 미래로 predict 돼 있다. 그 상태에 pose 를 그대로
update 하면 "과거 측정을 미래 상태에 잘못 정합"하게 된다. 구현:

- `imu_hist_`(원시 IMU 로그) + `state_hist_`(predict 스텝마다의 상태 스냅샷)를
  `retrodiction_window_`(기본 0.5s) 만큼 롤링 보관 (`imu_callback`).
- `mcl_pose_callback`: `pose.timestamp` 이하인 가장 최근 스냅샷을 찾아 **그
  시점으로 되감고(rollback)** → 거기서 `ekf_update_pose` 로 보정 → 그 이후
  버퍼링된 IMU 를 순서대로 재적용(replay)해 "현재"로 재전진. `state_hist_`는
  보정된 궤적으로 다시 채워진다(`imu_hist_`는 원시 로그라 그대로 재사용).
- 스냅샷이 없으면(보정치가 window 보다 오래됐거나 기능 꺼짐) 예전처럼 현재
  상태에 직접 update — 안전한 폴백.
- 알려진 근사: `t0`(스냅샷 시각)와 `pose.timestamp` 사이 잔여 갭(최대 1 IMU
  주기)은 predict 없이 바로 보정 — 개선 여지지만 영향은 미미(<10ms급).

### 11.2 A/B 실측 — 이득 확인 안 됨, 기본값 false로 결정

0730 bag(`22:52:38`, `/ekf/imu/data`+`/odom`+`/newmcl_pose`+`/mocap_pose1`
재생, `ROS_DOMAIN_ID` 격리)에 `retrodiction_enabled` 만 바꿔 A/B, `eval_loc_analyze.py`
(글리치 실측-스팬 판정 버전)로 비교 (steady, n≈15400):

| | p50 | p90 | p95 | MAX | yaw MAE | 종방향 편향 |
|---|---|---|---|---|---|---|
| retrodiction ON | 9.7cm | 25.1cm | 32.8cm | 80.0cm | 2.10° | +1.2cm |
| **retrodiction OFF** | **8.5cm** | **20.3cm** | **25.3cm** | 90.7cm | 2.35° | +0.4cm |

**결론: 이 bag/구성에서는 retrodiction이 위치 정확도를 오히려 소폭 악화시킨다**
(p50 +1.2cm, p90 +4.8cm). yaw만 소폭 개선(2.35→2.10°). 편향은 OFF도 이미
거의 0(+0.4cm)이라 애초에 retrodiction이 고칠 대상(지연으로 인한 체계적
"뒤처짐")이 이 bag엔 없었다.

**왜 이론과 다른 결과가 나왔나 (추정)**: §8.5.1의 26~46ms 지연 추정치는
record5 기준, **컨트롤러가 28.6Hz로 비동기 조회할 때** MCL pose 가 조회
시점에 얼마나 늙어있는지를 잰 것이다. 이번 0730 A/B 는 그 소비 패턴이 아니라
`/ekf_pose` 자체를 200Hz로 최대한 자주 발행하며 MCL(~51Hz)·IMU(~100Hz) 값을
그대로 흘려보낸 것 — 애초에 되감을 만한 지연/간격이 record5 시나리오보다
훨씬 작았을 가능성이 높다. 즉 **retrodiction이 "틀렸다"기보다, 이 bag이
retrodiction이 이득을 주는 조건(느린 MCL, 비동기 소비 지연)을 충분히
재현하지 못했을 가능성**이 있다 — 확정하려면 §8.5 와 동일한 "컨트롤러
조회시각 샘플링" 프로토콜로 재검증 필요(다음 후속 과제, 실차 불필요).

**결정**: 코드/파라미터는 유지, **기본값 `retrodiction_enabled: false`**.
이론적으로 더 올바른 설계라도 실측 이득이 없으면 기본으로 켜지 않는다는
이 문서의 기존 원칙(§9)과 일관됨.
